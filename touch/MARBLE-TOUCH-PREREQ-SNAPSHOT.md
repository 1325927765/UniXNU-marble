# Marble prerequisite snapshot prototype

`MarbleTouchPrereq.cpp` is a standalone, boot-argument-hookable XNU source module. It provides `marble_touch_prereq_snapshot()`, called once by `MarbleTouchProbe` only when `marbletouchprobe=3`. The Stage 3 kernel compiled successfully; the physical snapshot returned with error_mask=0, but its new kernel stayed at Logo; the same-kernel mode-0 control also stayed at Logo. See the repository STATUS.md. It has no clock, regulator, pinctrl, GPI, SPI, DMA, or SMMU write path. All device mappings use `kIODirectionIn` and `kIOMapReadOnly`. It reports raw SMMU ID/SMR/S2CR data, two decoded stream routes, three GPI contexts and five GPI status words, and six Cape TLMM config/I/O snapshots. No context-bank configuration or page-table walk is attempted.

## Source provenance

- Board DTS: `research/hardware-live-20261023-connected/marble-live.dts` identifies apps SMMU compatible `qcom,qsmmu-v500`, base `0x15000000`, length `0x100000` and `qcom,skip-init` at lines 18560–18570. The `qcom,num-smr-override=<0x78>` at line 18569 caps the working stream-matching entry count to 120. The stream register arrays live at GR0 offsets derived from the matching Marble ARM SMMU source: SMR[n] `0x800 + 4*n`; S2CR[n] `0xc00 + 4*n`. A 4 KiB snapshot mapping covers ID0/1/2 and all entries through index 119.
- Marble kernel: repository `research/touch-marble-official`, HEAD `48952ed36228217531482b39d5bef13e7fd808ec`. `drivers/iommu/arm/arm-smmu/arm-smmu.h:46–126` defines ID0 SMS/EXIDS/NUMSMRG/SID width, ID1 NUMCB, ID2 IAS/OAS/UBS, GR0 ID offsets, and the SMR/S2CR layouts. `arm-smmu.c:3630–3669` derives EXIDS from ID0, stream width and NUMSMRG, and clamps the count against `qcom,num-smr-override`. `arm-smmu.c:3454–3499` shows the actual split validity extraction: EXIDS uses S2CR.EXIDVALID; legacy uses SMR.VALID and excludes that bit from mask. `arm-smmu-qcom.c:36–60` snapshots raw SMR/S2CR and extracts route/context fields.
- Stream decoding uses the independent host-tested `marble_smmu_stream.c`; it consumes only the arrays read here. EXIDS mode is selected from the actual ID0 bit 8, not assumed. ID0/1/2 values that are zero or all ones, missing ID0.SMS, zero SMRG count, or too-narrow SID width reject the SME snapshot.
- Cape GPIO: the DTS `pinctrl@f000000` node at lines 1349–1359 establishes base `0x0f000000`, size `0x01000000`. `drivers/pinctrl/qcom/pinctrl-cape.h` in the same Marble HEAD defines `REG_BASE=0x100000`, `REG_SIZE=0x1000`, `ctl_reg=REG_BASE+REG_SIZE*pin`, `io_reg=ctl_reg+4`, and `mux_bit=2` in its PINGROUP macro (around lines 13–44). Its GPIO16–19 pins are QUP4 slots (lines 1642–1648); GPIO20/21 are still read only and are not decoded for SPI use. The mapped interval is only `0x116000` bytes and covers gpio16–21 cfg and io words.
- GPI DMA: the live DTS `qcom,gpi-dma@900000` node at lines 12425–12440 declares `reg=<0x900000 0x60000>` and `qcom,gpi-ee-offset=<0x10000>`. Marble `drivers/dma/qcom/gpi.c:3035–3068` maps `regs` at the resource start and derives `ee_base = regs - gpi_ee_offset`; it then computes channel/event context registers relative to `ee_base` at lines 3106–3139. The prototype maps only resource base `0x900000` (not the derived `0x8f0000` EE base) and subtracts the EE offset in the selected resource-relative register offsets. For GPII 0, `msm_gpi_mmio.h:7–8` places TX channel 0 context at top offset `0x20000`; `:48–49` places event context at `0x21000`; subtracting EE offset `0x10000` yields mapped offsets `0x10000` and `0x11000`. RX channel 1 is at `0x20080` -> mapped `0x10080`. Context CONFIG, R_LENGTH, ring base LSB/MSB are at `+0,+4,+8,+0xc` (`msm_gpi_mmio.h:80–95`). The DTS GPI channel request is TX channel 0/RX channel 1 for SE4 and the static mask chooses GPII0. The three contexts log their numeric state and EE fields only; no owner is asserted.
- GPI read-only status comes from `msm_gpi_mmio.h:100–168`: for GPII0 resource-relative offsets `0x13080`, `0x13090`, `0x13094`, `0x13100`, and `0x13118`. The source driver reads these status fields and handles them separately from their clear-register offsets. The prototype reads only these status words and never reads `GPI_GPII_n_ERROR_LOG_OFFS`, which the driver clears after reading (`gpi.c:851`); it does not access any clear register. `gpi.c:3041–3139` maps the device resource and assigns context registers; there is no GPI clock acquisition in this path, and the DTS GPI node has no clock property. A read-only GCC vote guard checks bits 6–9 before GPI reads, but this is only a conservative board guard and is not proof of GPI supply/clock accessibility. The GPI SMMU SID controls DMA transactions; this CPU MMIO snapshot does not attach to the SMMU or submit DMA.

## Safety limits and interpretation

The ID, array, GPI, and TLMM snapshots are a proposal for a future physical-device test, not evidence that XNU can safely access these physical mappings on a live kernel. Before any run, independently confirm the SoC mapping and access permission in the exact booted image. The source readout cannot establish the selected stream's translation correctness, CBAR/CBA2R state, active page tables, SMMU security/firewall reachability, TBU power, or GPI SID sharing. It must not be used to justify a DMA attempt or bypass. A `translate` route only says the captured S2CR type field is translation and reports CBNDX. A `bypass`, `fault`, ambiguous, absent, or invalid route is reported as such and causes no action. The GCC vote guard is not a hardware-accessibility proof for the GPI block.

The TLMM words are logged raw plus mux field `(cfg >> 2) & 0xf`; no mux, direction, pull, output, IRQ, or reset register is changed. The read path may still be inaccessible until a physical test establishes the mapping. Stage 3 integrates this read-only snapshot into the existing probe. All-ones TLMM cfg/I/O values set the capture-error bit. A zero error mask does not establish DMA safety.
